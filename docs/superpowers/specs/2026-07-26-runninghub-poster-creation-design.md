# RunningHub 海报图创作模块设计

## 1. 目标

将工作台中的“海报图创作”改造成独立、可维护的图片生成模块。模块沿用视频封面图的 RunningHub 调用基础设施，但使用适合无参考图场景的 G-2 文生图接口，不再调用 Ark 图片接口。

首期交付：

- 输入海报用途、主标题、辅助文案与视觉风格。
- 每次生成两张候选海报。
- 支持 1:1、3:4、9:16、9:25 四种比例族。
- 除 1:1 外，每种比例族均可切换横屏与竖屏，实际提交值分别为：
  - 3:4 / 4:3
  - 9:16 / 16:9
  - 9:25 / 25:9
- 结果区域按实际比例预览并支持逐张下载。
- 海报页面保持普通业务工具定位，不注册业务助理。

## 2. 方案选择

### 采用：海报独立模块，共享 RunningHub 基础能力

为海报建立独立的类型、提示词、客户端和后端任务接口。后端复用现有 `RunningHubClient` 的鉴权、HTTP 客户端、任务查询、轮询、错误归一化和文件下载能力，并新增 G-2 文生图提交方法。

该方案能保持海报和视频封面的业务边界，同时避免重复实现第三方服务接入。

### 不采用：扩展 `/api/video/cover`

视频封面接口要求参考图，并携带视频任务关联信息。让纯文生图海报复用该接口会增加大量条件分支，也会混淆任务、缓存和错误文案。

### 不采用：Next.js 直接请求 RunningHub

这会重复服务端密钥管理、轮询和文件落盘逻辑，并扩大 `RUNNINGHUB_API_KEY` 的暴露风险。

## 3. 模块边界

### 前端领域模块

`lib/poster/` 负责：

- 海报比例族、方向、分辨率和任务状态类型。
- 将“比例族 + 方向”解析成 RunningHub 实际比例字符串。
- 构建中文商业海报提示词。
- 提交任务、查询状态和轮询结果的浏览器客户端。

`components/poster/` 负责：

- `PosterCreationForm`：用途、文案、风格和比例设置。
- `PosterRatioSelector`：比例族与横竖方向选择。
- `PosterResultGallery`：空状态、生成状态、失败状态、结果预览与下载。

`components/poster-creation-workspace.tsx` 只负责编排状态和组合子模块，不直接了解 RunningHub 请求格式。

### Next.js API 代理

新增：

- `POST /api/poster/generate`
- `GET /api/poster/status`

路由只复用现有 FastAPI 代理边界，不持有第三方密钥或业务状态。

### FastAPI 领域接口

新增独立海报请求、提交响应和状态响应模型，以及：

- `POST /api/poster/generate`
- `GET /api/poster/status`

海报任务拥有独立任务前缀、内存状态表、后台任务表和缓存目录，避免与视频封面任务互相污染。

### RunningHub 客户端

在 `RunningHubClient` 中新增文生图提交方法，调用：

`/openapi/v2/rhart-image-g-2/text-to-image`

请求仅包含：

- `prompt`
- `aspectRatio`
- `resolution`

生成两张图时提交两个独立任务，以保持与 RunningHub 单任务返回一个结果的契约一致。两个任务并发等待，允许保留已成功的结果；仅当两张均失败时将整个海报任务标记为失败。

## 4. 数据流

1. 用户填写创作设置并选择比例族和方向。
2. 前端将选择解析为实际比例，例如 `9:16 + 横屏` 解析为 `16:9`。
3. 前端生成结构化提示词并向 Next.js 海报代理提交任务。
4. FastAPI 创建海报任务，立即返回本地任务 ID。
5. 后台并行向 RunningHub 提交两个 G-2 文生图任务并轮询。
6. 成功结果下载到本地海报缓存目录，状态接口返回稳定的本地媒体 URL。
7. 前端轮询状态，逐步展示阶段文案，成功后根据实际比例渲染两张结果。

## 5. 比例与横竖屏规则

页面展示四个比例族：

| 比例族 | 竖屏提交值 | 横屏提交值 |
|---|---:|---:|
| 1:1 | 1:1 | 1:1 |
| 3:4 | 3:4 | 4:3 |
| 9:16 | 9:16 | 16:9 |
| 9:25 | 9:25 | 25:9 |

选择 1:1 时隐藏或禁用方向切换。默认选择 3:4 竖屏，以匹配营销海报的常见使用场景。

预览容器使用解析后的实际比例，不固定为 3:4；极长比例设置合理的最大高度并使用 `object-contain`，避免裁切生成结果。

## 6. 提示词

提示词由纯函数构建，包含：

- 商业中文海报任务说明。
- 海报用途。
- 主标题和可选辅助文案。
- 视觉风格。
- 实际画面比例和横竖构图要求。
- 中文文字准确、层级清晰、合理留白、无水印、无二维码、无虚构品牌标志等约束。

前端必须要求主标题非空；后端再次校验提示词与比例，不能信任客户端。

## 7. 错误处理

- 缺少提示词或比例不受支持：返回 400。
- 缺少 `RUNNINGHUB_API_KEY`：沿用现有 503 配置错误。
- RunningHub 提交、查询或下载失败：写入任务错误和阶段文案。
- 一张成功、一张失败：任务仍返回成功结果，并附带候选图不足提示。
- 两张均失败：任务失败，前端展示可重试错误。
- 前端轮询设置总超时并在卸载时取消，避免页面切换后继续更新状态。

## 8. 计费和配置边界

- 继续使用现有 `RUNNINGHUB_API_KEY`，不新增环境变量。
- 不从云端同步的纯模型配置中替换 RunningHub 工作流或图片接口设置。
- 海报生成沿用现有图片业务的计费边界；本次不新增新的充值、扣费或退款机制。
- 不把“已提交任务”记录为生成成功，只有取得并缓存至少一张有效图片才进入成功状态。

## 9. 测试与验收

自动化测试覆盖：

- 比例族与方向解析。
- 1:1 方向无效化。
- 9:25 / 25:9 透传。
- 提示词内容与空值处理。
- RunningHub 文生图端点、负载和业务错误。
- FastAPI 参数校验、两任务并发和部分成功。
- 前端不再引用 Ark 图片客户端。
- 前端拥有独立表单、比例选择、方向选择、轮询、下载和自适应预览。
- 海报仍未注册业务助理。

验收以专项测试、Python 测试、TypeScript 类型检查和页面交互检查为证据。真实 RunningHub 生成只有在当前环境具备有效密钥并实际取得图片时才标记为外部调用验证通过。
