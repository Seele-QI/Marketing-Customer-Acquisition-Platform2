# 企业知识库官方联系方式设计规格

**日期：** 2026-07-22  
**状态：** 待实施  
**范围：** GEO 企业知识库搭建页、企业实体类型、Skill 生成接口与生成提示词

## 目标

企业在搭建 C 层知识库 Skill 时，必须完善一组可核验的官方联系方式。采集流程只要求联系人姓名和一种首选联系方式，避免长问卷占用客户精力。联系方式作为企业官方信息写入知识库 Skill，供后续内容在明确需要联系、咨询、预约或购买时按需引用。

本功能不把联系方式提交到 CRM，不建立新的后台客户线索库，也不改变 GEO 文章默认禁止主动输出联系方式的合规规则。

## 最小信息原则

生成企业知识库 Skill 前，只要求以下三项：

1. 联系人姓名。
2. 首选联系方式类型：手机、微信或邮箱三选一。
3. 与所选类型对应的联系方式值。

备用联系方式完全可选，默认收起。客户点击“添加备用联系方式”后，可再选择一种不同的联系方式类型并填写对应值。首期最多保存一个备用联系方式，避免表单膨胀。

企业名称、行业和核心产品沿用现有实体建模字段。本次不新增地址、营业时间、职位、部门、座机、社交媒体主页等非必要字段。

## 页面交互

“实体建模”卡片在核心产品字段下新增“官方联系方式”分区。

默认状态展示：

- 联系人姓名输入框。
- 首选联系方式类型选择器。
- 根据类型动态显示的单个输入框。
- “添加备用联系方式”轻量按钮。

客户选择手机时显示手机号输入框；选择微信时显示微信号输入框；选择邮箱时显示邮箱输入框。切换类型时清空旧类型的值，避免把手机号误标成微信号。

备用联系方式默认不占页面高度。展开后展示类型选择器、对应输入框和移除按钮；备用类型不得与首选类型重复。

字段标签明确标注“必填”或“选填”。页面不在首次进入时展示错误。客户点击“生成”后，只在缺失或格式错误的字段附近显示具体提示，并将焦点移到第一个错误字段。

## 数据模型

在 `GeoEntityData` 中新增结构化字段：

```ts
type GeoContactMethod = "phone" | "wechat" | "email"

type GeoOfficialContact = {
  contactName: string
  primary: {
    type: GeoContactMethod
    value: string
  }
  backup?: {
    type: GeoContactMethod
    value: string
  }
}

type GeoEntityData = {
  // 现有字段保持不变
  officialContact: GeoOfficialContact
}
```

客户端默认值为空。API 不信任客户端数据，必须重新清洗字段、限制字符串长度并校验联系方式格式。

为兼容旧调用方，类型迁移期间允许输入对象缺少 `officialContact`；但新的企业 Skill 生成请求必须通过服务端校验，否则返回 `400` 和可直接展示的中文错误信息。

## 校验规则

- 联系人姓名：去除首尾空白后必填，长度 2–30 个字符。
- 手机号：允许中国大陆常用 11 位号码，以及带国家/地区码的数字、空格、短横线和括号格式；去除首尾空白后长度 6–24 个字符。
- 微信号：去除首尾空白后长度 2–40 个字符，不强制使用过窄的历史微信号正则，避免拒绝手机号形式或企业自定义账号。
- 邮箱：采用轻量邮箱格式校验，长度不超过 254 个字符。
- 备用联系方式：填写时必须类型和值同时存在，且类型不得与首选类型重复。

错误信息不得回显请求体中的完整联系方式。日志不得记录完整联系方式。

## 生成与存储链路

1. `GeoEntityPanel` 收集官方联系人信息并写入 `GeoEntityData`。
2. `GeoSkillGeneratorPanel` 在生成前执行客户端校验，减少无效请求。
3. `/api/geo/enterprise-skill/generate` 对联系方式进行服务端清洗和校验。
4. `buildEnterpriseSkillUserPrompt` 将清洗后的联系方式作为“官方联系方式”输入区块提供给模型。
5. 生成提示词要求 Skill 正文包含“官方联系方式”章节，并逐字保留输入值，不推断、不补全、不改写。
6. 生成结果继续存入现有浏览器本地 `geo-enterprise-skills-v1`，不新增 CRM 或服务端联系人数据库。

联系方式会随企业 Skill 正文存储于浏览器本地，也会在生成时发送给用户选择的大模型服务。页面应在联系方式分区下以短说明明确告知这一点。

## Skill 输出契约

企业 Skill 正文新增以下固定章节：

```md
## 官方联系方式

- 联系人：张三
- 手机：13800000000
- 备用邮箱：service@example.com
- 使用边界：仅在用户明确要求联系、咨询、预约或购买时引用；不得主动插入普通内容。
```

模型不得：

- 编造缺失联系方式。
- 将联系人姓名扩写为职务或身份。
- 修改手机号、微信号或邮箱。
- 把官方联系方式描述成私人联系方式。
- 在其他章节重复堆叠联系方式。

如果模型输出遗漏或改写联系方式，接口应在返回前以确定性方式补齐或替换“官方联系方式”章节，确保保存的 Skill 与清洗后的输入一致，而不是再次调用模型。

## 下游引用边界

企业 Skill 中存在联系方式不代表所有内容都应展示联系方式。

- 内容矩阵只可使用企业事实，不在选题中主动植入联系方式。
- GEO 文章默认继续禁止联系方式和站外导流表达。
- 只有用户的创作任务明确要求“联系方式、咨询方式、预约方式、购买方式”等内容时，生成提示词才可引用企业 Skill 中的官方联系方式。
- 平台规则更严格时，以平台合规规则为准。

本次实现只保证企业 Skill 正确保存官方联系方式和使用边界；不修改现有 GEO 文章生成器的默认合规策略。

## 异常处理

- 缺少联系人姓名：阻止生成，提示“请填写联系人姓名”。
- 未选择联系方式类型：阻止生成，提示“请选择首选联系方式”。
- 联系方式为空或格式错误：阻止生成，提示当前类型的具体问题。
- 备用类型重复：阻止生成，提示“备用联系方式需选择其他类型”。
- 服务端收到旧客户端请求且缺少联系方式：返回 `400`，不扣除生成积分。
- 大模型生成失败：沿用现有错误处理，不保存半成品 Skill。

联系方式校验必须发生在积分扣除之前。

## 测试与验收

### 单元测试

- 官方联系方式清洗与三种类型校验。
- 联系人缺失、首选方式缺失、格式错误和备用类型重复。
- API 在校验失败时返回 `400`，且不会进入计费或模型调用。
- Prompt 包含清洗后的官方联系方式及使用边界。
- 生成结果遗漏或改写联系方式时，确定性输出修正能够恢复原值。
- 旧实体数据缺少 `officialContact` 时，页面能够加载，但不能生成新的 Skill。

### 组件测试

- 默认只显示一组首选联系方式。
- 切换联系方式类型只显示对应输入框并清空旧值。
- 备用联系方式可展开、移除且不能与首选类型重复。
- 点击生成后聚焦第一个错误字段。

### 验收标准

- 客户只填写联系人姓名和一种联系方式即可完成必要信息。
- 未完善必要联系方式时无法生成企业知识库 Skill。
- 生成的 Skill 准确包含官方联系人与联系方式，不被模型改写。
- 普通 GEO 文章不会因为知识库包含联系方式而自动输出导流信息。
- 联系方式不会被写入新的后台客户数据库或日志。
- 相关测试与 `npx tsc --noEmit` 通过。

## 非目标

- CRM 线索收集与销售跟进。
- 短信或邮箱验证码验证。
- 企业联系人多人管理。
- 联系方式的服务端长期存储与跨设备同步。
- 自动从上传文档提取联系方式。
- 修改平台发布或一键分发流程。
