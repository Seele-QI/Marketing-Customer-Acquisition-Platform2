# GEO 文章自动插图设计

**日期：** 2026-07-30

**状态：** 已确认设计，待实施计划

**范围：** GEO 优化 → 深度优化文章创作

## 1. 目标

在现有矩阵批量文章创作流程中接入与图片工作台同源的 RunningHub 图片生成能力。用户可以设置每篇文章自动添加 `0–5` 张插图，系统在文章完成后规划插图位置、并发生成图片并自动插入正文。

本功能必须满足：

- 默认每篇 `0` 张插图，不改变现有纯文章创作行为。
- 每个插图位置只生成 `1` 张最终图，不要求用户挑选候选图。
- 插图数量是“每篇文章”的数量，而不是整个批次的图片总数。
- 文章和插图任务均按矩阵项目隔离保存。
- 图片失败不应把已完成文章判定为失败。
- 页面切换后任务继续运行并保留进度。
- 页面、错误消息和帮助文案不得展示底层供应商或模型商品名。

## 2. 已确认 UI 方案

采用 **A 版：创作参数双列布局**。

### 2.1 插入位置

在文章批量创作面板中：

1. 矩阵项目
2. 发布日期
3. 矩阵继承信息
4. **创作参数双列**
   - 左侧：每组合篇数
   - 右侧：每篇插图 `0 1 2 3 4 5`
5. 批次生成统计
6. 开始创作按钮

插图数量选项不使用额外开关。`0` 本身代表关闭插图，避免“关闭”和“0 张”形成重复状态。

### 2.2 文案和状态

- 字段名：`每篇插图`
- 辅助文案：`系统根据标题与段落语义创作插图，并自动插入正文合适位置`
- 数量为 `0` 时：
  - 统计：`将生成 8 篇文章`
  - 按钮：`开始创作`
- 数量大于 `0` 时：
  - 统计：`将生成 8 篇文章 + 24 张插图`
  - 按钮：`开始图文创作`
- 创作中显示双进度：
  - 批次级：`文章 5/8 · 插图 12/24`
  - 文章级：`正文完成 · 插图 2/3`
- 图文全部完成后显示：`图文完成`
- 部分图片失败时显示：`文章完成 · 2/3 张插图 · 1 张待补`

## 3. 用户流程

1. 用户选择矩阵项目、发布日期、每组合篇数。
2. 用户选择每篇插图数量 `0–5`，默认 `0`。
3. 系统实时计算文章总数和预计插图总数。
4. 用户点击“开始创作”或“开始图文创作”。
5. 文章继续使用现有 SSE 批量生成流程。
6. 每篇文章生成成功后，立即创建该文章的插图计划，无需等待全部文章完成。
7. 插图任务进入全局受控并发队列。
8. 每张图生成成功后写入文章插图元数据，并插入 Markdown 正文对应位置。
9. 单张图片失败时自动重试；最终失败仅标记该图片，不影响文章成功状态。
10. 用户可以在文章卡片和正文编辑器中查看插图进度与最终图片。

## 4. 文章插图规划

### 4.1 规划输入

- 矩阵项目 ID
- 文章 ID、标题、正文 Markdown
- 发布平台
- 矩阵格的内容方向、文章格式和 GEO 意图
- 企业知识库中允许公开引用的品牌视觉信息
- 用户选择的插图数量

### 4.2 可插入锚点

先解析格式化后的文章结构，将正文拆成语义块。可选锚点必须满足：

- 位于主要正文小节内部或其后。
- 有明确的小节标题或完整段落语义。
- 同一锚点最多插入一张图。

排除以下位置：

- 首行标题与开场第一段之间。
- 官方联系方式、地址、电话、微信、邮箱区域。
- 总结、免责声明、FAQ 和标签行。
- 已有图片相邻位置。
- 空段落和过短段落。

### 4.3 数量分配

- 从可用锚点中按正文顺序均匀选择目标数量。
- 优先覆盖不同小节，避免图片集中在文章前半段。
- 若合格锚点少于用户选择数量，只生成安全可插入的实际数量，并在进度中显示：`计划 5 张 · 实际可插入 3 张`。
- 不通过复制同一锚点或把图片塞进联系方式、FAQ、标签区来凑数。

### 4.4 图片提示词

每个锚点生成一个独立的图片提示词，包含：

- 文章主题与当前小节语义。
- 发布平台的视觉表达建议。
- 企业品牌中可公开使用的主体、行业和风格信息。
- 禁止出现的敏感信息和不应绘制的联系方式。
- 无文字或少文字优先，避免模型生成乱码。
- 不生成二维码、联系方式、虚构证书、虚假票据和绝对化承诺。

提示词由服务端构建，客户端不能覆盖底层模型、工作流 ID 或供应商参数。

### 4.5 图片规格

用户不额外选择尺寸，系统按发布平台自动匹配，统一使用 `1k` 分辨率：

| 平台 | 图片比例 |
|---|---|
| 小红书、微博 | `3:4` |
| 抖音 | `9:16` |
| 大众点评、携程 | `4:3` |
| 知乎、网易、搜狐 | `16:9` |
| 未知兼容平台 | `4:3` |

同一篇文章内所有自动插图保持同一比例和视觉方向。手工上传的图片不强制裁剪。

## 5. 技术架构

### 5.1 不直接复用图片工作台公开 API

现有图片工作台 API 固定生成两张候选图，适合人工选择，不适合文章自动插图。

新增文章插图专用 API，复用图片工作台底层能力：

- RunningHub workflow 调用适配器。
- 云端下发的工作流和模型配置。
- 状态轮询与错误映射。
- 结果下载和本地静态缓存。
- 积分计费与幂等引用。

专用 API 每个插图位置只产生一张最终图片。

### 5.2 接口合同

#### 提交文章插图批次

`POST /api/geo/article-illustrations/generate`

请求：

```json
{
  "projectId": "matrix-project-id",
  "articleId": "article-id",
  "platformId": "zhihu",
  "markdown": "文章正文",
  "count": 3
}
```

返回：

```json
{
  "taskId": "illustration-batch-id",
  "articleId": "article-id",
  "plannedCount": 3,
  "items": [
    {
      "id": "illustration-item-id",
      "anchorId": "section-2-paragraph-1",
      "status": "queued"
    }
  ]
}
```

#### 查询批次状态

`GET /api/geo/article-illustrations/status?taskId=...`

返回每个插图项的：

- `queued`
- `generating`
- `success`
- `failed`
- `retrying`

成功项必须包含稳定的图片 URL、锚点信息、替代文本和完成时间。

### 5.3 FastAPI 任务层

新增独立的文章插图任务存储和后台执行器，不与图片工作台的“两张候选图”任务结构混用。

任务层职责：

- 校验 `count` 为 `0–5`。
- 解析文章锚点并生成插图计划。
- 为每个锚点提交一次 RunningHub 图片任务。
- 使用全局信号量控制并发，默认同时执行 `6` 张图片，不新增用户可见配置。
- 单张图片最多自动重试 `2` 次，使用退避等待。
- 下载结果并保存到文章插图专用缓存目录。
- 对外只返回产品级错误文案。

缓存路径：

```text
public/geo-article-illustrations/<projectId>/<articleId>/<illustrationId>.png
```

服务端必须校验归一化后的项目、文章和插图 ID，禁止路径穿越。

## 6. 数据结构与项目隔离

### 6.1 批量配置

`ArticleBatchConfig` 新增：

```ts
illustrationsPerArticle: 0 | 1 | 2 | 3 | 4 | 5
```

该字段随矩阵项目批次配置保存。旧缓存不存在该字段时按 `0` 处理。

### 6.2 文章结构

`GeneratedArticle` 新增：

```ts
illustrationTaskId?: string
illustrationStatus?: "none" | "planning" | "generating" | "partial" | "success"
illustrationPlannedCount?: number
illustrations?: Array<{
  id: string
  anchorId: string
  url: string
  alt: string
  status: "queued" | "generating" | "success" | "failed"
  error?: string
}>
```

文章和插图任务继续使用 `projectId` 分区。任何读取、合并、重试和编辑操作都必须同时校验 `projectId + articleId`，不同矩阵项目的数据不能合并展示。

### 6.3 Markdown 插入

图片成功后插入：

```md
![与当前小节相关的简洁替代文本](/static/geo-article-illustrations/...)
```

同时保留结构化 `illustrations` 元数据，供：

- 编辑器预览。
- Markdown 导出。
- 后续一键分发提取图片。
- 单张补图和错误恢复。

不得只修改 Markdown 而丢失结构化图片记录。

## 7. 并发与进度

### 7.1 调度方式

- 文章任务保持现有有限并发。
- 某篇文章一旦完成，立即提交该文章的插图批次。
- 插图任务在所有文章之间共享一个全局并发池。
- 不使用 `文章数 × 插图数` 的无上限 `Promise.all`。
- 图片任务完成顺序不影响文章原始排序。

### 7.2 任务恢复

客户端按矩阵项目持久化：

- 插图批次 `taskId`。
- 文章 ID。
- 计划数量与完成数量。
- 已成功图片 URL。
- 最后查询时间。

GEO 页面切换时组件保持挂载。浏览器刷新后，根据本地任务快照重新查询未完成任务，不重复提交已经成功或仍在执行的 RunningHub 任务。

## 8. 计费与幂等

- 使用云端配置的图片创作计费场景，不在前端硬编码单价。
- 每个插图项拥有稳定的幂等引用：

```text
geo-article-illustration:<projectId>:<articleId>:<illustrationId>
```

- 自动轮询、页面恢复和同一任务重试不能重复扣费。
- 只有真正发起新的 RunningHub 插图任务才进入计费链。
- 前端可以显示预计插图数量；积分预估只在已有价格查询能力可用时显示。

## 9. 错误处理

| 场景 | 行为 |
|---|---|
| 文章生成失败 | 不创建插图任务，沿用文章失败处理 |
| 插图规划无安全锚点 | 文章成功，插图状态为 `none`，说明无合适位置 |
| 单张图片生成失败 | 自动重试两次 |
| 重试后仍失败 | 文章保持成功，插图状态为 `partial` |
| 状态查询短暂失败 | 按现有错误预案退避重试，不弹出立即失败提示 |
| 页面切换 | 任务继续，返回后恢复当前进度 |
| 浏览器刷新 | 从项目任务快照恢复轮询 |
| 底层服务信息 | 统一改写为“图片创作服务暂时繁忙”等产品级文案 |

批次结束提示：

- 全部成功：`图文创作完成，共 8 篇文章、24 张插图`
- 部分图片失败：`8 篇文章已完成，22/24 张插图已生成，2 张可稍后补图`
- 不使用“整批失败”覆盖已经成功的文章结果。

## 10. 兼容性

- `illustrationsPerArticle = 0` 时不调用任何图片 API，现有文章链路和计费保持不变。
- 旧文章没有插图字段时按纯文章正常展示。
- 现有手工“插图”上传按钮继续保留，可用于替换或补充自动插图。
- 图片工作台继续保持两张候选图逻辑，不受文章插图专用 API 影响。
- 一键分发暂不自动发布插图，但结构化图片元数据必须为后续接入保留。

## 11. 验收标准

### UI

- 可选择 `0–5` 张，默认 `0`。
- 用户明确看到这是“每篇”数量。
- 统计正确计算文章数和插图数。
- 数量大于 `0` 时显示图文创作进度。

### 功能

- 选择 `0` 时没有图片 API 调用。
- 选择 `1–5` 时每篇成功文章生成对应的安全插图计划。
- 每个位置只生成一张最终图片。
- 图片并发受到全局上限控制。
- 图片自动插入正确正文位置。
- 联系方式、FAQ、总结和标签区域不插图。
- 单张失败不会把文章改成失败状态。
- 页面切换和刷新后不重复创建任务。
- 不同矩阵项目的文章、图片和任务互不混合。

### 安全与产品文案

- 客户端无法指定底层模型、工作流或供应商。
- 浏览器错误和 UI 不展示 RunningHub、workflow ID 或模型商品名。
- 文件路径经过规范化和归属校验。
- 重试和恢复不会重复扣费。

## 12. 测试范围

- 插图数量 clamp、旧缓存默认值和总数计算。
- Markdown 锚点解析、排除区和均匀分配。
- 图片 prompt 不包含联系方式和内部配置。
- API 参数、认证、项目归属和路径校验。
- FastAPI 全局并发上限和单项重试。
- 任务状态恢复与计费幂等。
- 项目级缓存隔离。
- 纯文章模式回归。
- 文章成功、插图部分失败的 UI 状态。
- Next.js 类型检查和生产构建。

## 13. 非本期范围

- 用户逐张选择两张候选图。
- 用户自选图片模型、工作流或供应商。
- 在批量创作前编辑每张图片 prompt。
- 自动将插图发布到第三方平台。
- 图片在线裁剪、画布编辑和复杂重排。
