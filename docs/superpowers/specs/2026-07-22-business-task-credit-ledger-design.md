# 业务任务级积分流水设计

## 目标

积分仍按真实底层调用逐笔扣除并保留审计明细，但用户侧流水只展示完整业务任务的总消耗。数字人视频创作需汇总口播文案规划、音色克隆、视频生成及付费重试；GEO 需按一次用户发起的完整生成任务汇总。普通聊天、提取文案、改写等零散小额扣费不再出现在用户流水中。

## 展示口径

- 数字人视频：一次从创作开始到成片完成的工作流显示为一条“数字人视频创作”。
- GEO：一次文章批次、内容矩阵生成或企业知识技能生成分别显示为一条完整任务记录；其内部模型调用合并到该任务。
- 聚合金额是任务关联流水的净变动；消费显示负数，任务内退款会抵减任务总消耗。
- 聚合备注展示阶段构成，例如“口播文案 20 + 音色克隆 10 + 视频生成 900，共 930 积分”。同类阶段出现多次时先合计再展示。
- 充值、注册赠送、管理员调整及无法归属到任务的退款始终单独展示。
- 普通聊天、提取文案、改写以及其他未声明为业务任务的消费仍真实入账并影响余额与累计消耗，但不进入用户流水。
- 历史消费没有可靠业务任务标识，不按时间或备注猜测合并；历史小额消费隐藏，历史充值、赠送、调整和退款保留。

## 数据模型

在现有 `credit_ledger` 上增加三个可空字段，保持旧数据库兼容：

- `business_task_id`：一次完整业务任务的稳定分组键。
- `business_type`：受控业务类型，如 `video_digital_human`、`geo_article_batch`、`geo_matrix`、`geo_enterprise_skill`。
- `billing_stage`：受控阶段，如 `script`、`voice_clone`、`video_generation`、`video_retry`、`llm_generation`。

`ref_id` 继续只承担单次扣费幂等职责，不与 `business_task_id` 混用。现有唯一索引、余额计算和原始账本审计逻辑保持不变。启动时以幂等迁移补齐字段和查询索引。

## 任务标识传递

### 数字人视频

前端在开始一次新创作时生成业务任务 ID，并在同一草稿生命周期内持久保存。口播文案规划、音色克隆、视频分段生成及付费重试均把该 ID 传给服务端。开始全新创作或显式重置工作流时生成新 ID，刷新或恢复当前草稿时沿用原 ID。

服务端不信任客户端提供的展示名称，只接受受控 `business_type` 和 `billing_stage`；用户归属仍由登录会话确定。业务任务 ID 不替代各阶段现有的幂等键。

### GEO

每次用户点击生成时创建或沿用该生成作业的业务任务 ID：

- 文章批次使用批次/作业 ID，批次内全部模型调用归入同一任务。
- 内容矩阵使用单次生成作业 ID，同次生成的内部调用归入同一任务。
- 企业知识技能使用单次生成作业 ID。

研究、权威链接抓取等辅助调用只有在明确携带所属生成任务 ID 时才并入该任务；否则作为隐藏的底层消费，避免错误归组。

## 账本写入接口

现有 `consume`、定价注册表扣费和计量扣费链路增加可选的业务任务上下文。未提供上下文时行为与当前一致。上下文在服务端经过长度、字符和枚举校验后随原始流水一起写入。

退款优先从原消费记录继承业务任务上下文，使任务展示净消耗；无法定位原消费时仍作为独立退款展示。幂等命中不新增流水，也不重复累计任务金额。

## 查询与响应

用户侧 `/api/credit/ledger` 改为返回展示账单，而不是原始调用明细：

1. 非消费型可展示流水逐条保留。
2. 带受支持业务任务上下文的消费与关联退款，按用户、业务类型和业务任务 ID 聚合。
3. 不带业务任务上下文的消费过滤掉。
4. 聚合任务的时间取首次消费时间，余额取该任务最后一笔流水的 `balance_after`，排序位置取最后一笔流水时间。
5. 接口按最终展示记录数返回最近 20 条，查询底层明细时分批读取，避免过滤后不足 20 条。

响应项增加 `entry_kind`、`business_type`、`business_task_id` 和 `breakdown`。现有 `type`、`delta`、`balance_after`、`note`、`created_at` 保留，前端可平滑渲染充值等单笔记录。

## 前端体验

“最近积分流水”改为“最近任务账单”，说明文字明确“按完整业务任务汇总展示，零散模型调用不单列”。

业务任务行展示易懂的类型名称、总积分变化、任务结束时余额与阶段构成。充值等单笔记录沿用现有布局。页面不暴露业务任务 ID、底层 `ref_id` 或模型调用明细。

## 失败与一致性

- 业务任务上下文缺失不会阻断现有扣费，只会使该消费不在用户流水展示。
- 非法业务类型或阶段由服务端拒绝，避免任意客户端污染账单分类。
- 聚合查询只读原始流水，不维护第二份可漂移的汇总余额。
- 余额、累计消耗、幂等和对账继续基于原始流水；展示聚合不参与财务计算。
- 同一个 `business_task_id` 在不同用户之间严格隔离；不同 `business_type` 不会互相合并。

## 测试与验收

测试先行，覆盖以下行为：

- 数字人脚本、音色、多个视频段与重试汇总为一条，并给出正确阶段明细。
- GEO 批次内多次模型扣费汇总为一条，不同批次不串账。
- 任务内退款抵减总消耗；独立退款仍显示。
- 普通聊天、提取文案和旧消费不显示，但余额与累计消耗不变。
- 充值、赠送和管理员调整正常显示。
- 幂等重复调用不重复计入任务金额。
- 过滤与聚合后仍尽量返回请求的展示条数。
- 旧数据库自动补齐字段，新旧流水可同时查询。
- 前端类型名称、总额、余额、说明文案及空状态渲染正确。

完成单元测试、TypeScript 类型检查，并对积分页面做一次浏览器级验证。没有真实完成端到端任务时，只能报告自动化验证结果，不宣称生产任务全链路已验证。

## 非目标

- 不删除原始积分流水。
- 不修改现有积分价格。
- 不对历史消费做时间窗口猜测聚合。
- 不建设独立的第二套业务账单表或后台审计页面。
- 不把所有产品功能都强制改造成可见业务任务；本次只覆盖数字人视频和明确的 GEO 完整生成任务。
