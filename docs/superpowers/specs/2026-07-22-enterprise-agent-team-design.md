# 企业部门智能体团队重构设计

- 日期：2026-07-22
- 状态：已批准
- 适用项目：`zhongtai-main`
- 交付方式：在现有 Next.js / FastAPI / Electron 双服务架构上增量实现

## 1. 背景

当前“智能体团队”使用名人姓名和头像展示七个顾问角色，但角色配置只包含名称、说明、标签、状态和快捷提示。通用 Agent API 仍固定使用同一套小红书提示词，没有把卡片角色传入服务端，也没有角色级 Skill、知识权限、模型路由、跨部门会签或工具审批。

本次重构将其升级为公司部门智能体系统：底层由云端下发模型，用户只选择部门或任务，不感知具体模型；系统通过角色契约、Skill、知识库、工具权限与审计链形成可验证的专业能力。

## 2. 已批准的产品决策

1. 采用“两层团队”：10 个通用企业部门，加 4 个 AI 内容中台行业专家。
2. 采用分级执行模式：分析和草稿可自动完成；高风险外部动作必须人工审批。
3. 使用严肃、职业化的原创虚拟角色，不再模拟公众人物。
4. 头像由绘图模型生成，采用统一的“企业编辑肖像”风格。
5. 用户不选择模型。云端下发候选模型和路由策略，管理员可查看实际路由。
6. 采用平台、公司、任务三层知识体系；法务、财务、人事默认严格隔离。
7. 支持图片与文件上传。附件默认只属于当前任务，明确选择后才可沉淀入库。
8. 跨部门协作采用“一个主责部门，加零至三个会签部门”。
9. 设计分三阶段实现，不把未完成或未真实验证的能力包装为成功。

## 3. 目标与非目标

### 3.1 目标

- 用公司职能替换名人顾问展示，并保持卡片、搜索、快捷提示和聊天入口一致。
- 建立可版本化的 Agent Registry、Skill Registry、Policy Engine、Model Router 和 Run Store。
- 让单部门任务保持简单，让复杂任务可自动形成主责和会签关系。
- 支持图片、PDF、DOCX、XLSX、PPTX、TXT、MD 和 CSV 的受控上传与解析。
- 让每次回答能追踪角色、Skill、知识来源、模型路由、费用、工具与审批。
- 对外发送、发布、写入和生产变更使用可恢复的人工审批。
- 以单元、集成、角色评测和浏览器端到端测试验证能力。

### 3.2 非目标

- 首版不新建独立微服务平台，不引入 OpenHands 等完整 Agent 平台替换现有系统。
- 首版不让用户直接选择 GPT、Claude、DeepSeek 等底层模型。
- 智能体不取得律师、会计师、审计师等执业身份，也不替代最终签字人。
- 未配置外部账号、API 或真实 UAT 的连接器不得标记为可用。
- 不允许模型自主付款、签约、盖章、录用、解雇或作出具有法律效力的最终批准。

## 4. 设计依据

- Agent Skills 使用渐进加载：会话开始只暴露名称与描述，命中任务后加载完整 `SKILL.md`，再按需读取资源。这样可以避免把全部部门知识塞入基础提示词。[Agent Skills：Adding Skills Support](https://agentskills.io/client-implementation/adding-skills-support)
- 多智能体采用 Manager/agents-as-tools 模式：一个总协调角色保留最终交付责任，专业角色作为受控子任务执行者。[OpenAI Agents SDK：Agent Orchestration](https://openai.github.io/openai-agents-js/guides/multi-agent/)
- 工具调用使用输入/输出 Guardrail；涉及外部影响的工具使用可恢复人工审批。[OpenAI Agents SDK：Guardrails](https://openai.github.io/openai-agents-js/guides/guardrails/)、[Human in the Loop](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)
- 财务 Skill 可参考公开金融服务工作流的建模、表格审计和人工签署边界，但必须改造成经营财务与中国企业内控场景。[Anthropic Financial Services](https://github.com/anthropics/financial-services)
- 生成式 AI 风险治理采用“治理、映射、测量、管理”的持续闭环，而不是一次性安全检查。[NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)
- 中国境内的数据、个人信息、生成内容标识和企业内控遵循官方规则与公司适用范围。[生成式人工智能服务管理暂行办法](https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm)、[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)、[小企业内部控制规范](https://www.mof.gov.cn/gkml/caizhengwengao/2017wg/wg201708/201711/t20171108_2746247.htm)

公开 Skill 或社区资料仅作为结构参考。任何来源不明、许可证不清或缺少前向测试的 Skill 不直接进入生产。

## 6. 角色契约

### 6.1 专业等级

- O4：只负责分诊、委派、合并、冲突处理和风险升级。
- P3：能形成专业工作底稿、备选方案、行动建议、假设和待确认项。
- P4：用于法务、财务、技术数据等高风险角色，要求来源、日期、口径、复核步骤和人工签署提示。P4 不代表执业资格。

### 6.2 统一输出约束

每个角色都必须：

1. 区分已知事实、附件内容、联网资料和模型推断。
2. 对高风险结论提供来源、发布日期、适用范围和置信度。
3. 说明缺失资料、关键假设和可能影响。
4. 使用“结论、依据、风险、建议动作、需人工批准事项”收尾。
5. 不把排队、提交、静态检查或模型输出包装成外部动作成功。

### 6.3 角色语言与越权边界

| 角色 | 固定语言风格 | 标准结构 | 禁止越权 |

## 7. Skill 体系

### 7.1 Skill 结构

每个 Skill 是一个可版本化包：

```text
skill-id/
├── SKILL.md
├── references/
├── scripts/
├── templates/
└── manifest.json
```

`manifest.json` 至少包含：`id`、`version`、`name`、`description`、`riskLevel`、`requiredTools`、`allowedRoles`、`sourceType`、`license`、`evaluationSet` 和 `enabled`。

加载顺序：

1. 基础上下文只加载 Skill 目录信息。
2. 路由器根据任务和角色选中 Skill。
3. 加载完整 `SKILL.md`。
4. Skill 明确引用时才读取模板、脚本和参考资料。
5. 运行记录保存 Skill ID、版本和实际加载资源。

## 8. 知识库与附件

### 8.1 三层知识库

1. 平台知识：官方法规、标准、公开规则和经过审核的通用模板。
2. 公司知识：品牌、制度、产品、合同、财务、组织、客户和运营资料。
3. 任务资料：当前会话上传的图片和文件，默认有生命周期并自动过期。

知识对象至少包含：租户、部门、密级、来源、所有者、创建时间、有效期、版本、文件哈希、解析状态和可访问角色。

### 8.2 角色知识范围

- 法务：国家法律法规、网信办、市场监管合同示范文本、公司合同和授权制度。
- 财务：财政部准则、公司科目口径、预算、流水、发票和经营报表。
- 人事：劳动法规、岗位库、员工手册；候选人与员工资料单独隔离。
- 技术：代码、架构、API、日志、数据字典和安全基线。
- 营销与内容：品牌规范、用户画像、市场研究、历史内容、平台规则和效果数据。
- 销售、公共事务、运营：只读取获授权的 CRM、合作方、媒体、工单、SOP 和客户资料。
- 行业角色：读取与视频、GEO、内容和分发任务直接相关的资料，不自动获得财务、人事或合同全文。

### 8.3 图片与文件上传

首版支持：

- 图片：PNG、JPG/JPEG、WEBP。
- 文件：PDF、DOCX、XLSX、PPTX、TXT、MD、CSV。

处理管线：

1. 校验文件签名、扩展名、MIME、大小、页数、压缩比和租户配额。
2. 计算哈希并创建任务附件记录。
3. 执行恶意文件、宏、外链和敏感信息检查。
4. 图片使用 OCR 和多模态理解；文档提取文本、页码、表格和版面位置。
5. 将附件内容视为不可信数据，屏蔽其中试图修改系统规则的提示注入。
6. 用户可查看解析状态、删除附件或选择沉淀范围。
7. 默认只进入任务临时区；入库必须明确选择并保留原文件、提取物和版本关系。

单文件解析失败不得使其他附件丢失。系统说明失败文件、影响范围和重试建议，任务保持 `partial`。

## 9. 工具权限与审批

### 9.1 权限等级

- T0 自动只读：知识检索、联网查证、附件解析、状态查询。
- T1 自动生成：草稿、分析、内部临时文件；必须保存版本和来源。
- T2 人工审批：邮件、日历邀请、平台发布、CRM/工单写入、生产变更。
- T3 禁止代办：付款、盖章、合同签署、录用解雇、法律和审计最终签字。

### 9.2 审批契约

审批记录必须展示：发起角色、工具、对象、完整参数或差异、预计费用、外部影响、有效期和撤销/回滚说明。

审批绑定任务版本、工具参数哈希、草稿版本和发起人。任何内容变化都会使旧审批失效。执行完成后保存外部返回值、资源 ID、时间和验证证据。

## 10. 云端模型路由

### 10.1 用户体验

- 前台不显示模型选择器。
- 用户看到“自动路由、预计积分、当前服务状态”。
- 管理员可以查看角色实际模型、提供商、路由原因、降级链和费用。

### 10.2 路由输入

路由器使用：任务类别、角色、风险等级、多模态需求、结构化输出需求、上下文长度、工具能力、提供商健康、预算和云端策略版本。

### 10.3 路由行为

1. 云端同步候选提供商、模型、能力标签、优先级、价格和启用状态。
2. 任务开始时生成不可变路由快照。
3. 只在同一权限和能力等级内降级，不允许降级绕过安全约束。
4. 设置任务总预算、模型调用数、会签数和工具费用上限。
5. 所有提供商均不可用时明确返回 `failed`，不伪造回答。

## 11. 跨部门编排

### 11.1 模式

- 用户直接选择部门：该部门是主责；只有出现明确高风险交叉点时才邀请会签。
- 用户选择纪衡：纪衡先结构化分诊，再确定一个主责和零至三个会签部门。
- 主责角色拥有最终工作底稿；会签只给结构化意见，不直接夺取用户会话。

### 11.2 会签输入与输出

会签部门只收到：任务摘要、被授权附件或附件片段、所需问题、输出 Schema、截止时间和权限快照。

会签输出至少包含：结论、风险等级、依据、建议、阻断项、缺失资料和置信度。

### 11.3 冲突处理

纪衡不得消除真实分歧。最终结果应并列展示冲突意见、各自依据、影响和建议决策人。

## 12. 系统架构

### 12.1 Next.js 控制面

- 智能体中心和对话工作台。
- 附件、引用、会签进度、审批卡和任务历史。
- 身份、租户、积分和服务端 API 代理。

### 12.2 Agent Runtime

首版作为仓库内聚模块实现，而不是独立服务：

- Agent Registry：角色契约、快捷任务、状态和版本。
- Orchestrator：主责、会签、结果合并与状态机。
- Skill Loader：发现、校验、渐进加载和版本快照。
- Policy Engine：知识 ACL、工具权限、风险和审批。
- Model Router：云端配置、能力匹配、预算和降级。
- Run Store：事件、引用、费用、错误、审批和最终产物。

### 12.3 FastAPI / Electron 能力面

- 文档、表格、PPT、OCR 和知识解析。
- 视频生成、ffmpeg、GEO、发布和数据工具。
- 本机浏览器或 Electron 才能完成的受控连接器。

## 13. 数据模型

至少包含以下实体：

- `agent_definitions`：角色 ID、版本、状态、契约、等级、头像、默认 Skill、允许工具。
- `skill_definitions`：Skill ID、版本、风险、来源、许可证、资源清单、评测状态。
- `knowledge_documents`：租户、部门、密级、来源、版本、哈希、解析状态和生命周期。
- `agent_runs`：任务、用户、主责、状态、预算、路由快照、角色快照和最终结果。
- `agent_run_members`：主责/会签角色、输入摘要、状态、输出、错误和时间。
- `agent_run_events`：模型、Skill、知识检索、工具、费用、状态变化和审计事件。
- `agent_approvals`：工具参数、哈希、风险、审批人、状态、有效期和执行证明。
- `agent_attachments`：文件元数据、解析物、任务范围、知识范围和删除状态。

数据库写入必须包含 `user_id` 和租户范围。服务端不得信任客户端传入的角色权限、知识范围或模型 ID。

## 14. API 边界

建议新增：

- `GET /api/agents`：返回用户可见角色、可用状态和展示信息。
- `GET /api/agents/:id`：返回角色详情、Skill 摘要、知识范围和工具等级。
- `POST /api/agent-runs`：创建任务、上传引用、设置主责或进入自动分诊。
- `GET /api/agent-runs/:id`：读取任务快照与当前状态。
- `GET /api/agent-runs/:id/events`：SSE 读取状态、消息、会签、工具和费用事件。
- `POST /api/agent-runs/:id/messages`：追加用户消息或补充资料。
- `POST /api/agent-runs/:id/cancel`：取消任务。
- `POST /api/agent-runs/:id/approvals/:approvalId`：批准或拒绝并恢复执行。
- `POST /api/agent-attachments`：上传图片或文件并创建解析任务。
- `POST /api/agent-attachments/:id/promote`：经授权沉淀到公司或部门知识库。

旧 `/api/agent/chat` 在兼容期内转发到新 Runtime，不能继续使用固定小红书 System Prompt。

## 15. UI 设计

### 15.1 智能体中心

- 顶部突出“总协调官·纪衡”。
- 使用经营治理、产品技术、市场增长、交付服务、行业专家分组。
- 卡片显示原创头像、姓名、职位、专业等级、三项主要 Skill 和真实服务状态。
- 状态只允许“可用、需配置、服务异常、暂停”，不再随机显示在线、忙碌或空闲。
- 搜索支持角色、部门、Skill 和任务类型。

### 15.2 对话工作台

- 标题显示当前主责或纪衡跨部门任务。
- 模型只显示“自动路由”，不暴露底层模型选择。
- 输入区支持图片、文件、知识范围和审批策略。
- 右侧协作栏显示主责、会签、状态、风险和审批卡。
- 回答显示文件页码、表格位置、网页来源和会签分歧。
- 任务历史可恢复 `needs_review`、`partial` 和失败任务。

## 16. 原创头像

采用企业编辑肖像风格：

- 1:1 胸像，正面或轻微侧身，统一人物比例和视线高度。
- 柔和棚拍光、中性低饱和背景、克制的商务服装。
- 通过部门背景色、服装细节和配饰区分角色，不使用文字水印。
- 保持年龄和性别自然多样性，不使用岗位刻板印象。
- 不使用公众人物、真实员工或受保护品牌标志。
- 对眼睛、手部、徽标、乱码、真人相似度和跨图一致性进行人工质检。

## 17. 状态与错误处理

任务状态：

- `queued`
- `preparing`
- `running`
- `needs_review`
- `partial`
- `completed`
- `failed`
- `cancelled`

规则：

- 附件解析失败或会签失败但已有可用结果时为 `partial`。
- 外部工具处于“已提交”时不能标记 `completed`。
- 用户未审批时停在 `needs_review`，不得调用外部工具。
- 只有产物、必需会签、引用、费用和执行证明齐全时才可 `completed`。
- 取消任务应停止后续模型和工具调用，同时保留已有审计记录。

## 18. 安全要求

- 按用户、租户、部门、任务和密级执行服务端 ACL。
- 上传资料视为不可信内容，防止提示注入修改系统指令、权限或工具参数。
- 云端密钥和完整配置不进入浏览器。
- 角色、Skill、模型、知识范围和工具权限在任务开始时保存快照。
- 工具参数使用严格 Schema、超时、重试上限、幂等键和结果验证。
- 个人信息、合同、财务和人事材料使用最短生命周期与访问审计。
- 不向模型发送与当前任务无关的历史会话、附件或内部提示词。

## 19. 费用与审计

- 创建任务时估算预算并设置硬上限。
- 每次模型、会签、工具和多模态调用记录实际费用。
- 降级、重试和失败均写入事件流；不对失败调用重复扣取不合理费用。
- 管理员可按用户、角色、模型、Skill 和任务查看费用与错误率。
- 用户只看到任务总消耗和需要额外批准的费用，不选择底层模型。

## 20. 测试与评测

### 20.1 单元测试

- Agent Registry Schema、唯一 ID、名称和角色映射。
- Skill 发现、版本、渐进加载、冲突和禁用。
- Model Router 的能力匹配、预算、快照、降级和无可用模型。
- Policy Engine 的知识 ACL、工具等级、审批和跨部门最小上下文。
- 附件类型、大小、恶意输入、解析失败和生命周期。
- 状态机、取消、幂等、partial/completed 门禁。

### 20.2 集成测试

- 使用 Mock Provider 验证分诊、主责、会签和结构化合并。
- 验证失败会签不会丢失主责结果。
- 验证审批前不会调用 T2 工具，修改参数会使审批失效。
- 验证模型降级保留同一权限并写入路由事件。
- 验证积分结算与实际调用一致。

### 20.3 角色评测

每个角色至少包含：正常任务、资料缺失、越权诱导、提示注入四类用例。法务、财务、技术数据增加来源过期、错误数字、不可复现证据和高风险执行测试。

### 20.4 浏览器端到端测试

覆盖选择角色、交给纪衡、上传图片与文件、附件失败、查看会签、进入审批、拒绝、批准、任务恢复、取消和历史记录。

### 20.5 真实 UAT

邮件、日历、CRM、发布或任何真实外部动作均需使用单账号、低频、可撤回或低影响场景进行 UAT。只有获取真实外部结果证明后才标记连接器可用。

## 21. 分阶段交付

### 阶段 1：可用团队

- 14 个角色和原创头像。
- Agent Registry、基础 Orchestrator、Skill 目录和云端模型自动路由。
- 图片与文件临时附件。
- 一个主责、最多三个会签。
- 引用、风险、预算和基础审计。
- 角色与浏览器测试。

### 阶段 2：企业知识与审批

- 三层知识库、部门 ACL 和入库审核。
- 安全解析、生命周期和版本管理。
- 统一审批中心、恢复执行和完整事件流。
- 角色与 Skill 评测后台。

### 阶段 3：外部执行

- 逐个接入邮件、日历、CRM、工单和平台发布连接器。
- 每个连接器具备审批、幂等、结果验证和错误回传。
- 逐渠道真实 UAT；未验证能力保持 `partial` 或 `需配置`。

## 22. 阶段 1 验收标准

1. 现有名人卡片全部替换为 14 个职业角色，名称、职位、头像、Skill 和快捷任务一致。
2. 用户可直接选择部门或交给纪衡；复杂任务最多三个会签。
3. 前台不显示模型选择器，管理员可追踪实际模型、降级和费用快照。
4. 图片和首版文件类型可上传、解析、删除，并明确临时或知识范围。
5. Skill 激活可追踪，未匹配 Skill 不加载。
6. 高风险动作不可绕过审批；拒绝、过期和内容修改后的状态正确。
7. 失败附件、失败会签和外部未验证步骤不会被标记为完成。
8. 单元、集成和浏览器端到端测试通过。

## 23. 设计自检结论

- 无 `TBD`、`TODO` 或未定义占位需求。
- 角色数量、姓名、等级、Skill、知识范围和 UI 展示一致。
- 首版、知识权限和外部执行三个阶段边界明确。
- 模型隐身不等于模型不可审计：管理员仍可查看路由快照。
- “支持外部动作”与“外部动作已真实验证”明确区分。
- 本设计可以拆成单一实施计划，并按三个阶段顺序执行。
